# План: PROFIBUS-DP slave-симулятор на RP2040

## Цель и рамки

Устройство на второй RP2040, подключённое к той же RS-485 линии, что и тестируемый
profirust-master (RP2040, до 12 Мбит/с). Устройство эмулирует **N независимых DP-V0
slave** (у каждого свой адрес, ident_number, размеры входов/выходов, диагностика и
поведение) — для тестирования master'а, включая сценарии отказов.

- Протокол: **PROFIBUS-DP V0** (DP-V1 не нужен: profirust-master работает по V0,
  реальный IL PB BK DP/V1 тоже работает в режиме V0).
- Эталон совместимости — поведение реального slave (IL PB BK DP/V1) и, главное,
  ожидания profirust-master: `src/dp/peripheral.rs`, `src/dp/master.rs`.
- Аппаратура: одна RP2040, один UART + RS-485 трансивер (как в `examples/rp-pico`),
  USB CDC для управления/отладки.

Термины (кратко):
- **TSDR** — пауза slave между концом принятого запроса и началом своего ответа.
  Минимум 11 битовых времён (задаёт master в Set_Prm). Отвечать раньше нельзя.
- **slot_time (Tsl)** — сколько master ждёт ответ после запроса (у profirust
  `slot_bits` в параметрах). Ответ должен начаться: TSDR ≤ t < slot_time.
- **SAP** — номер сервиса в заголовке телеграммы (какой сервис адресован).
- **FCB** — бит в теле запроса: если master повторил запрос с тем же FCB, slave
  должен повторить свой прежний ответ, а не выполнять запрос заново.
- **SC** — short confirmation, подтверждение в 1 байт (0xE5).
- **PI_I / PI_Q** — образ процесса: входы (slave→master) / выходы (master→slave).
- **Slave_Diag** — ответ с диагностикой: 6 стандартных байт статуса + опциональные
  блоки расширенной диагностики.

## Архитектура

Три части; протокольная логика живёт в библиотеке (тестируется на ПК без железа),
фirmware — тонкая.

### 1. Библиотека profirust (новые модули)

- `src/fdl/passive.rs` — `FdlPassiveStation`: приём телеграмм по своему адресу и
  broadcast, ответ в окно TSDR, дедупликация по FCB (повтор запроса → повтор
  сохранённого ответа), ответ на FDL-status запрос.
- `src/dp/slave.rs` — `DpSlave`: машина состояний DP-V0 (WPRM → WCFG → DXCHG),
  разбор входящих запросов (Set_Prm, Chk_Cfg, Global_Control, Data_Exch, Slave_Diag
  запрос, опц. RD_Inp/RD_Outp), формирование ответов (SC, данные, диагностика),
  watchdog.
- Переиспользовать как есть: `src/fdl/telegram.rs` (парсинг/сериализация телеграмм,
  `TelegramTx` уже умеет собирать все нужные ответы), `src/consts.rs` (все slave-САПы
  уже есть), `src/phy/*`, `src/time.rs`.
- Заполнить пробелы: сериализация Slave_Diag (6 байт + ext-diag блоки;
  формат — как разбирает `handle_diagnostics_response` в `src/dp/peripheral.rs`,
  биты — `DiagnosticFlags` там же), парсинг PDU запросов (Set_Prm 7+байт, Chk_Cfg,
  Global_Control 2 байта).

API (ориентировочно):
```rust
let mut slave = dp::DpSlave::new(DpSlaveOptions {
    address, ident_number, pi_i: &mut [u8], pi_q: &mut [u8], ..
});
// один slave = один FdlPassiveStation поверх DpSlave
fdl_passive.poll(now, &mut phy, &mut slave);
```
Для мультислейва — вариант без владения PHY: `slave.handle_telegram(t) -> Reply`
(см. «Multi-slave»).

Тесты (на ПК, `cargo test`): интеграционные — реальный `dp::DpMaster` против
N × `DpSlave` на виртуальной шине `src/phy/simulator.rs` (она уже проверяет
коллизии и соблюдение TSDR/TID). Отдельные unit-тесты: FCB-повторы, формат
диагностики, watchdog.

### 2. Firmware: `examples/rp-pico-slave/` (новый crate)

- Диспетчер: один `phy::Rp2040Phy`, поверх — N экземпляров `DpSlave`.
- Главный цикл без блокировок: принять телеграмму → определить адрес назначения →
  передать нужному экземпляру → отправить ровно один ответ.
- Конфигурация slave — статическая таблица в коде (файл `slaves.rs`), поля:
  адрес, ident_number, длина PI_I/PI_Q, содержимое ext-diag, поведение
  (эхо выходов во входы / константы / счётчики), сценарий отказов.
- USB CDC (как в примере rp-pico, логирование через кольцевой буфер с другого ядра
  или в main loop — не в горячем пути): команды — задать значения входов slave,
  прочитать его выходы, включить/выключить инъекцию аварий/диагностики, статус.

### 3. Тестовая оснастка

- Сценарии (ниже) прогоняются как в host-тестах, так и на реальной шине.
- Логический анализатор (GPIO-пины отладки, см. `examples/rp-pico`) для замера
  фактического TSDR и времени реакции.

## Протокольная матрица (что реализовать)

| Входящий запрос | SAP | Ответ slave |
|---|---|---|
| FDL-status (FC = request FdlStatus, без SAP) | — | Data: FC = Response{Slave, Ok}, пустой PDU (чтобы `dp::scan` видел slave) |
| Set_Prm (SRD) | 61 | **SC**. Парсить: station status (Lock_Req, WD_On + факторы 1/2, Sync/Freeze req), min_tsdr, ident_number, groups. Несовпадение ident → не принимать (остаться WPRM, в диагностике Prm_Fault). Запомнить master address (byte 3 diag) |
| Chk_Cfg (SRD) | 62 | **SC**. Сверять конфигурацию модулей с ожидаемой (задаётся в настройках slave); несовпадение → Cfg_Fault, остаться WCFG |
| Global_Control (SDN, broadcast DA=127) | 58 | Без ответа. Обработать Clear / Operate / Sync / Freeze + group-маску; отразить в битах диагностики (Sync_Mode, Freeze_Mode) |
| Data_Exch (SRD, без SAP) в DXCHG | — | Data: FC = Response{Slave, **Ok/DL**} (или **DH**, если появилась новая диагностика — это сигнал master'у забрать Slave_Diag), PDU = PI_I ровно настроенной длины |
| Data_Exch в WPRM/WCFG | — | Data: FC = Response{Slave, **RS** (SapNotEnabled)} — profirust-master это обрабатывает (переходит к перевалидации конфигурации) |
| Slave_Diag (SRD) | 60 | Data (dsap=62, ssap=60): 6 байт статуса + ext-diag блоки. Байты: status1, status2, status3 (bit0 = Ext_Diag_Overflow), адрес master (255 если не параметрирован), ident_number (big-endian). Биты — `DiagnosticFlags` из `src/dp/peripheral.rs`; бит PERMANENT (status2 bit2) всегда = 1 |
| RD_Inp / RD_Outp (SRD) | 56 / 57 | Data с PI_I / PI_Q (для полноты, невысокий приоритет) |
| Любой SRD с тем же FCB, что и предыдущий (FCV=1) | — | Повторить **сохранённый** ответ, запрос не выполнять. Смена FCB → выполнить и сохранить новый ответ |

Watchdog (если в Set_Prm был WD_On): нет обращений дольше factor1 × factor2 × 10 мс
→ выходы в безопасное состояние (нули), переход в WPRM, в диагностике выставить
Prm_Req (status1 bit0) — master переустановит параметры.

## Тайминги (критично на 12 Мбит/с)

- Ответ начинать не раньше `min_tsdr` (из Set_Prm, ≥ 11 бит) после последнего байта
  запроса и до истечения slot_time master'а. На 12 Мбит/с 11 бит = 0.92 мкс;
  при `slot_bits` = 300 бюджет master'а ~25 мкс. Целевое время реакции firmware —
  единицы микросекунд.
- `phy::Rp2040Phy` полудуплексный и поллинговый (RX из FIFO UART, TX с задержкой
  Tset, переключение dir-пина уже реализованы). Главный цикл не должен блокироваться
  дольше глубины FIFO UART (32 байта ≈ 30 мкс на 12 Мбит/с): USB-лог и консоль —
  только по кольцевому буферу, без printf в горячем пути.
- Не отвечать раньше TSDR — это проверяет и `SimulatorPhy` в тестах, и реальный master.
- Порядок ввода скоростей: ≤ 500 кбит/с (простые тайминги) → 1.5 / 3 / 6 → 12 Мбит/с
  с замером логическим анализатором. Если на 12 Мбит/с поллинг не успевает —
  UART IRQ на приём байта в кольцевой буфер (минимальный ISR).

## Multi-slave на одном UART

- RS-485 приём promiscuous: диспетчер видит все телеграммы, разбирает заголовок
  (`fdl::Telegram::deserialize`), смотрит DA:
  - DA = адрес экземпляра → обрабатывает и отвечает он (ровно один ответ на запрос);
  - DA = 127 (broadcast, Global_Control) → обрабатывают все экземпляры, никто не
    отвечает;
  - FDL-status → отвечает экземпляр с этим адресом (каждый slave виден для `dp::scan`).
- Коллизий не бывает: master опрашивает slaves по одному.
- Память: ~0.5 КБ на slave (PI + diag + состояние); 8–16 slave — без проблем.
- Ограничение: один и тот же PHY нельзя использовать из двух мест — ответы
  сериализуются через диспетчер (это учтено в API `handle_telegram → Reply`).

## Сценарии тестирования (входят в требования)

1. Полный старт master'а: обнаружение slave → диагностика → Set_Prm → Chk_Cfg →
   диагностика (без флагов ошибок) → циклический обмен.
2. Циклический обмен: эхо PI_Q → PI_I, корректность `cycle_completed`.
3. Диагностика: включить ext-diag → master получает событие Diagnostics и корректные
   блоки; выключить → DH-сигнал пропадает.
4. Отказы: slave молчит полностью; отвечает с битым CRC; отвечает поздно (за
   пределом slot_time); выставляет Prm_Fault / Cfg_Fault; RS-ответ; пропуск каждого
   k-го ответа (проверка retry-логики master'а); watchdog → Prm_Req.
5. Переходы Clear/Operate, команды Sync/Freeze (проверка битов в диагностике).
6. Несколько slave одновременно (3–8) с разными ident_number и размерами PI.
7. Устойчивость на 12 Мбит/с: длинный прогон, замер TSDR и потерь байт.

## Этапы

| Этап | Содержание | Критерий готовности |
|---|---|---|
| M1 | `fdl::passive` + unit-тесты (SC, FDL-status, FCB-повторы, окно TSDR) | тесты зелёные |
| M2 | `dp::slave` + интеграционные тесты `DpMaster` ↔ N × `DpSlave` на `SimulatorPhy` | сценарии 1–5 зелёные на ПК |
| M3 | firmware, один slave, реальная шина, ≤ 500 кбит/с | стабильный цикл с реальным master'ом, диагностика работает |
| M4 | multi-slave (3–8), USB-управление, инъекция отказов | сценарии 6 + отказы на реальной шине |
| M5 | 1.5 → 12 Мбит/с, замеры таймингов, оптимизация (IRQ при необходимости) | сценарий 7 |

## Источники истины в коде (на что опираться при реализации)

- Что master отправляет и что ждёт в ответ: `src/dp/peripheral.rs`
  (`transmit_telegram`, `receive_reply`, `handle_diagnostics_response`), Global_Control
  — `src/dp/master.rs`.
- Форматы телеграмм, FC, FCB, ответы: `src/fdl/telegram.rs`.
- Биты диагностики: `DiagnosticFlags` в `src/dp/peripheral.rs`.
- Параметры/тайминги: `src/fdl/parameters.rs` (`min_tsdr_bits`, `slot_time`,
  `watchdog_factors`).
- Виртуальная шина для тестов: `src/phy/simulator.rs` (уже проверяет TSDR-задержки).
- Аппаратная часть PHY: `src/phy/rp2040.rs`, пример firmware: `examples/rp-pico/`.
- Поведение реального slave (эталон): IL PB BK DP/V1; описание состояний DP-slave:
  WPRM → WCFG → DXCHG (см. PROFIBUS-литературу, «States of the DP slave», Felser;
  диагностика — «Diagnostic coding», Felser).

## Риски и допущения

- 12 Мбит/с: байт каждые 0.92 мкс — предел поллингового приёма; страховка —
  UART IRQ (этап M5) или работа мультислейва на 6 Мбит/с.
- `Rp2040Phy::receive_data` паникует, если вызван во время передачи — диспетчер
  обязан соблюдать порядок «принял → ответил → снова слушаю».
- Реакция на Data_Exch в WPRM/WCFG как RS (SapNotEnabled) выбрана под profirust-master
  (он это обрабатывает); при сертификации с другими master'ами может потребоваться
  вариант с ответом диагностикой.
- Ведение slave другому master'у (Lock_Req/адрес в диагностике) — упростить: всегда
  отвечать на запросы, адрес master'а запоминать из Set_Prm.
